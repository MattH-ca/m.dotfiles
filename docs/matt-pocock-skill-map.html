Matt Pocock Skill Map

The question this page answers: which skill do I reach for, and how does work flow between them? The collection is not a flat toolbox - it is one main flow (idea to ship), three on-ramps that merge into it, a vocabulary layer underneath, and bridges for crossing context windows. The glue between skills is files in your repo, not direct calls.

The layers, one by one

main flow Idea to ship

/grill-with-docs interviews you to sharpen the idea, retaining what it learns in CONTEXT.md and ADRs. Small builds go straight to /implement; big ones pass through /to-spec and /to-tickets first.

/implement is a composite: it drives /tdd internally one red-green slice at a time, then closes with /code-review before committing. Both also work standalone.

Context hygiene rule: keep grilling through ticketing in one unbroken window (the ~120k-token "smart zone"), then run each /implement in a fresh session.

on-ramps Where work arrives

  • /triage - moves raw incoming issues through triage roles into agent-ready briefs that /implement picks up. Never for tickets /to-tickets made - those are already agent-ready.
  • /diagnosing-bugs - refuses to theorise until one command reproduces the bug red; fixes with a regression test. Hands off to the upkeep loop when the real finding is a missing seam.
  • /wayfinder - for efforts too big to hold in one session. Charts decision tickets on the tracker, resolves them one at a time, then merges at /to-spec. It hands off; it never builds.

vocabulary The layer underneath

Two model-invoked references, each the single source of truth for its words:

  • /domain-modeling - the project's domain language: challenge fuzzy terms, resolve overloaded words, record hard-to-reverse decisions as ADRs. /grill-with-docs drives it to keep CONTEXT.md a clean glossary.
  • /codebase-design - deep-module vocabulary (module, interface, depth, seam, adapter, leverage, locality). /tdd and /improve-codebase-architecture both speak it.

bridges Crossing sessions

  • /handoff - compacts the conversation into a markdown file; you open a new session against it. The bridge in both directions of the /prototype detour. Forks.
  • /compact (built-in) - stays in the same conversation, summarising earlier turns. Use at intentional phase breaks, never mid-phase. Continues.

Rule of thumb: /handoff forks; /compact continues.

standalone Off the main flow

  • /grill-me - same interview as /grill-with-docs but stateless, for plans with no repo. Both wrap the /grilling primitive.
  • /prototype - throwaway program answering one design question. Keep the answer, delete the code.
  • /research - background agent reads primary sources, leaves a cited markdown file that feeds /grill-with-docs.
  • /teach - multi-session learning in the current directory.
  • /bro - restate the last message in plain language.
  • /resolving-merge-conflicts, /writing-great-skills - situational references.
  • /ask-matt - the router over all of the above.

precondition One-time setup

/setup-matt-pocock-skills runs once per repo before the first engineering flow. It writes the config the other skills assume:

  • Issue tracker choice (GitHub, GitLab, local .scratch/ markdown, or freeform)
  • The five triage labels (needs-triage, needs-info, ready-for-agent, ready-for-human, wontfix)
  • Domain doc layout (single CONTEXT.md or a monorepo CONTEXT-MAP.md)
Not yet run in this repo (no docs/agents/ in dotfiles) - the tracker-dependent skills (/to-tickets, /triage, /to-spec, /wayfinder) assume it.

Shared state: how skills actually talk to each other

No skill invokes another across sessions. They coordinate through files committed to (or scratched into) the repo.
